# Headroom panel and scaling probes: design

> **Status: on hold** (2026-11-20). Superseded in sequence by `2026-11-20-standard-foundation-design.md`; to be rewritten for the Standard foundation once it lands.

Date: 2026-11-19. Follows `docs/neural-curriculum-v2-results.md`.

## Why

Curriculum v2 finished without a clear gain over curriculum v1, and the user
asked whether to rearchitect the model. The answer depends on whether the
current model is still limited by scale or by its design. Today we cannot tell:

- On both 64-case development panels, the trained policies already score at
  or above the search reference (39/64).
- On those panels, gaps of 4–6 wins are not significant.
- Act 2 and act 3 bosses, the weakest area, have only 6 cases each.

The user's decision rule is **lack of progress means rearchitect**. If making
the current model bigger, or training it longer, does not produce measurable
progress, the next project is a redesign. If either does, scaling stays the
cheaper path.

## Goals

1. **A headroom panel.** A held-out evaluation panel of 256 cases, weighted
   toward the fights we lose, with a per-tier search reference, so better
   policies can show it.
2. **Two scaling probes on curriculum v2**, each changing one thing and run
   with both existing seed pairs:
   - **Width:** `hidden_width` 64 → 256.
   - **Length:** 4× the training decisions.
3. **A comparison point.** The four existing curriculum v2 checkpoints are
   re-scored on the headroom panel without retraining:
   - `cv2` and `cv2-r2` are the comparison points for the probes.
   - `cv2-hp` and `cv2-hp-r2` are re-scored for information.
4. **A verdict** using the rule below, written up in a results doc.

## Non-goals

- Any architecture change. This round only decides whether one is warranted.
- Settling the HP-shaped reward question. The probes use the win/loss
  objective so they compare against `cv2`.
- Changing the existing 64-case panels or curricula; old results must stay
  comparable.
- Hyperparameter tuning beyond the one variable each probe changes.

## Anti-goals

- **A panel that leaks training data.** Cases must come from held-out
  material, never the train split.
- **Moving the goalposts.** The progress rule below is fixed before any probe
  result is seen. It is recorded in the results doc as pre-registered.
- **Using the final-evaluation split.** It stays untouched for a later final
  evaluation.

## The headroom panel

**Source.** Cases come from the curriculum v2 recipe's `selection` split,
generated by the existing v2 generator. Act 2 and act 3 bosses therefore use
real boss decks where the recipe says so.
- Selection shard 0 is excluded, because the current development panel uses it.
- *Builder's call:* how many further shards to draw from in order to fill the
  quotas.
- *My call:* if a tier cannot fill its quota from at most 64 further selection
  shards, panel building fails closed. Quotas are never silently shrunk, and
  synthetic decks are never used as fillers.

**Quotas.** These are the user-approved shape, with exact numbers as my call:

| Tier | Cases |
| --- | ---: |
| act1 boss | 32 |
| act1 elite | 32 |
| act2 boss | 48 |
| act2 elite | 40 |
| act3 boss | 48 |
| act3 elite | 40 |
| act2/act3 monster (hallway) | 16 |
| **Total** | **256** |

- Act 4 is excluded. It is about 1% of scenarios and was 0–1 of 1 in every arm.
- **Case rules:**
  - each case has a unique composition;
  - each case passes `validate_entry`;
  - `case_id`s are deterministic, derived from the recipe sha and quota slot;
  - each case gets its own `selection` environment seed, distinct from the
    development panel's.
- **Determinism:** building the panel twice from the same recipe gives the
  same bytes, and a test pins this.
- **Real-deck overlap.** Real-deck boss cases may repeat a recorded base deck
  that also appears in train with different extra cards; the results doc
  already states this limit. *My call:* annotate each real-deck case with its
  `run_id` and report results with and without cases whose `run_id` also
  appears in the train shards used, so this overlap is measured rather than
  assumed. "Train shards used" means the shards consumed by either run in the
  pair being compared. The `run_id` comes from the real-deck fields the
  generator already places in the case.

**Evaluation settings.**
- **Headroom panel only:** `case_actions` rises from 256 to 1024, so long
  real-deck boss fights finish instead of being censored. *My call:* this is a
  per-panel override, so the existing 64-case panels keep 256 actions and stay
  comparable with earlier results.
- *My call:* `case_seconds` scales to match; the builder sets it from measured
  fight lengths.
- Censored cases stay censored and are excluded from paired tests.

**Integration.** The baseline entry evaluates the headroom panel alongside the
existing panels; the existing `additional_panels` mechanism is the natural
place.
- `--reevaluate` must be able to score prior checkpoints on it, so that the
  four `cv2` arms can be re-scored. *My call:* today `--reevaluate` refuses a
  plan that differs from the original. Relax that check so the plan may differ
  only in its evaluation panels and evaluation settings. Every
  training-relevant field must still match exactly, and the differences are
  recorded in the output.
- *Builder's call:* how the plan names the panel, for example a panel kind
  next to recipe paths.

**Search reference.**
- Run the existing `boss_winnability.py` search player on all 256 cases.
  *My call:* extend it to read a panel manifest, and raise `max_steps` to 1,200
  so the search is not cut off before the policies are.
- Report per-tier search wins next to the policies.
- Use a larger budget than the gate's 8 samples / 40 playout steps. *My call:*
  32 samples and 80 playout steps, reduced if a 256-case pass would exceed
  about 6 hours of CPU time.
- **Standard rules only.** The Gym's `PublicSearch` only plays
  `standard-combat-v1`; there is no M10 search. So the reference remains an
  approximate, Standard-rules number, labelled as such. It describes headroom;
  it is not a cap.

## The probes

Each probe copies the `baseline-gym-1.1.1-cv2` plan and template, both seed
pairs, and changes only the following.

**Width probe (`cv2-w256`, `cv2-w256-r2`).**
- `hidden_width` = 256; `embedding_width` stays 16.
- The parameter count must stay under `max_parameters` (10,000,000); raise the
  cap only if the count exceeds it, and record it.
- Model config hashes change accordingly.
- Everything else is identical, including the learning rate.

**Length probe (`cv2-x4`, `cv2-x4-r2`).**
- `target_learned_decisions` = 1,622,016 (4 × 405,504).
- `max_training_decisions` and `max_optimizer_steps` rise to fit.
- `wall_seconds` and `runner_timeout_seconds` scale to about 4×, and the
  `gpu_wait` cap is sized to the longer run.
- **Retained checkpoints:** keep the cv2 points (135,168 and 270,336) plus
  405,504 and 811,008, so the curve shows the cv2-length point and the
  halfway point.

**Shared settings.**
- Learner, gym revision (`e3c13836`) and curriculum v2 recipe (real decks) are
  unchanged.
- Each run evaluates the headroom panel (primary for this study), the v2
  development panel and the v1 development panel.
- **GPU use:** the probes may use all GPU time not used by Hermes, through the
  existing `gpu_wait` gate. Runs are sequential.
- *My call:* the run order is width r1, width r2, length r1, length r2, so the
  shorter probe reports first.

## Progress rule (pre-registered)

The comparison uses final checkpoints on the headroom panel, pairing each probe
replicate with the `cv2` run that has the same seeds (r1 with `cv2`, r2 with
`cv2-r2`). A probe **makes progress** if both conditions hold:

1. **Both seed pairs agree:** in each pair, the probe wins more cases than its
   `cv2` partner. Both runs in a pair play each case with the same
   environment seed and deterministic action selection. A case censored in
   either run is dropped from that pair, for both rules.
2. **The pooled gain is significant:**
   - Pool both pairs' discordant cases into one exact two-sided McNemar test.
   - Run it twice: on all paired cases, and on act 2 plus act 3 boss cases
     alone. Progress needs either one to pass.
   - The boss-only test is the second of two tests, so each test uses
     p < 0.025 (Bonferroni).
   - The comparison is always final checkpoint against final checkpoint; for
     the length probe, that means 4× decisions against 1×.
   - A probe that is significantly worse counts as no progress, and the
     results doc reports that it was worse.

**Verdict.**
- If **neither** probe makes progress, recommend rearchitecting.
- If **one or both** make progress, recommend continuing to scale along the
  axis that helped.
- In both cases, report effect sizes and per-tier tables, so the decision is
  not just a p-value.

*Power note:* with 512 paired cases, the test can detect a difference of
roughly 4–5 percentage points. Smaller real gains would read as no progress,
and the doc says so.

## Constraints

- AGENTS.md applies:
  - public observations only;
  - no training on panel cases;
  - artifacts stay out of Git;
  - the real-deck table stays local;
  - simulator faults are errors, not losses.
- Tests are deterministic and CPU-only, and cover:
  - panel quotas, determinism and disjointness from the train split and from
    selection shard 0;
  - reevaluation on the new panel;
  - the probes' config validation.
- Every experiment records its gym revision, dirty state, recipe sha, panel
  sha, seeds, budgets and GPU waits.

- Shard counts for filling the quotas.
- `case_seconds`.
- The exact budget fields for the length probe.
- Whether search work runs while the GPU runs train (they use different
